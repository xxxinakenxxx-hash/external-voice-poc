# 【営業AIメモ】実装指示書 MAIL-03｜旧日次メール廃止・統合確認

作成日：2026-11-04／状態：指示書作成・実装未着手  
前提：MAIL-00～02の作業とユーザー確認が終わり、朝メールへの旧日次機能統合、および週間メールの検証が成立していること。未確認なら着手しない。

## 1. 目的・対象
旧`daily_manager`の日次定期メール配信を、朝メールへの情報統合を確認してから廃止する。続いて朝・週間の定期配信と北九州を統合検証し、公開判定に必要な証跡を整える。**単独で新機能を追加しない。**

## 2. 廃止対象と手順
- 関連候補：`triggerDailyReport`、`src/06_output.gs`内の日次メール本文・配信入口、`output_config`内の日次設定と時間トリガー。MAIL-00の参照関係を根拠に操作対象を特定する。
- 朝メールが`manager`・`president`へ本人情報＋配下まとめを正常生成できる証跡を先に確認する。
- 旧日次メールの**新規配信を停止**する。過去の`daily_manager`ログは保持し、共通集計／メール送信関数は他機能への参照がある場合は削除しない。
- 既存トリガーがすでに存在しない場合は、その事実を報告し、不要な新規作成・削除をしない。
- コードの物理削除・関数名変更は必須要件ではない。必要なら依存関係と変更対象を示し別承認を得る。

## 4. 変更対象・禁止範囲
変更対象はMAIL-00で特定した旧日次メールの配信入口・既存設定・トリガーに限定。朝メール・週間メールの追加改修が必要と判明した場合、MAIL-01またはMAIL-02へ差し戻し、同じ工程で勝手に修正しない。Git未追跡・未コミット差分を保護し、`todo_tasks`、`deal_records`、過去ログ、入力／画面機能、Googleカレンダー、Google Chat、認証情報を対象外とする。

## 5. 確認証跡
- 3役職×朝・週間の本文例、対象ユーザー・営業所・管轄会社の判定根拠、元行ID、元データと集計件数の対照、AI選定理由の根拠。
- 北九州の天気地点・交通なし・地域別ログ・送信対象、旧日次停止前後のトリガーと`push_log`の状態。
- 設定時刻、失敗時の通知・ログ、重複防止。
- 静的／隔離／GAS反映／トリガー変更／実メール送信／受信者側到達確認を分ける。受信側の協力が得られない場合は「到達未確認」とする。

## 6. 実施・停止・公開判定
- 旧日次停止やトリガー変更、`clasp push --force`、デプロイ更新、実メール送信はそれぞれ対象・理由・影響・復旧手段を説明し個別承認を得てから実施。
- `clasp push --force`は対象外差分を含めないこと、構文・回帰確認が通ることを条件とする。危険なら未実行で停止。
- 本番トリガーの再作成やテスト実送信は自動実施しない。ユーザーの公開判断前に「完了確定」と報告しない。
- 不一致・配下誤混入・ToDo権限不整合・既存朝メール停止・重複配信懸念があれば停止し、原因・差戻し先・証跡を報告する。
- `TASK_CURRENT.md`へ許可済み操作と未確認を区別して記録し、ユーザーへ実施場所・操作・期待結果を具体的に依頼する。次の別案件・工程へは進まない。
