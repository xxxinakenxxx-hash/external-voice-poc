# 【営業AIメモ】実装指示書 MAIL-02｜週間メール再設計

作成日：2026-11-04／状態：指示書作成・実装未着手  
前提：MAIL-00の調査承認済み、MAIL-01が検証・ユーザー確認済み、対象データ・本人ToDo権限の問題を明示判断済み。

## 1. 目的・対象
`triggerWeeklyReport`と関連する週間メール処理を再設計し、毎週月曜日午前8時台（JST）に有効な`sales`・`manager`・`president`へ個別メールを生成できるようにする。旧`weekly_manager`の既存処理はそのまま再開せず、役職別集計・本文・宛先・配信設定を見直す。

## 2. 変更対象候補
`src/06_output.gs`内の`triggerWeeklyReport`および週次集計・メール本文・送信・配信ログ関連関数。必要なマスタ・ToDo本人取得の共通関数、`output_config`の設定・トリガーはMAIL-00で調査し、変更範囲を承認する。**既存朝メール・旧日次メール・画面・DB構造は原則変更しない**。新規関数・ファイルや変更対象追加が必要なら停止して承認を得る。

## 3. 配信・期間
- 月曜午前8時台。対象は有効な`sales`・`manager`・`president`。
- 先週＝前週月～日、今週＝当週月～日（JST）。
- 先週集計：`sales`本人、`manager`本人＋所属営業所の営業担当者全員、`president`管轄会社全体。
- 今週予定・計画（暫定）：**全役職とも本人の記録・本人のToDoのみ**。他人の予定と`todo_tasks`は参照しない。
- `president`の本人ToDoは現行role権限の未解決課題。2026-10-06のTASK_CURRENTには対象外と記録されているが、現行実装はMAIL-00で確認する。MAIL-00で計画書と本指示書を証拠に基づき改訂する。現行で取得可能ならその条件を採用し、取得不可なら必要な変更を明示する。ユーザー承認なく権限を拡張せず、本仕様を満たせない場合は停止・報告する。

## 4. 本文5項目と算出方法
1. **先週の活動実績**：商談レコード件数、訪問活動回数、電話活動回数。商談のAI分割と1活動回数を区別し、元入力の識別方法を確認。判別不能な数値は推測表示しない。社長職は会社全体＋営業所別内訳。
2. **先週の主な商談**：全役職で最大5件。優先順「緊急対応（クレーム・納期等）→具体的進展（見積・受注等）→失注・停滞懸念→今後の営業機会」。顧客・案件テーマ・要点・選定理由を示し、根拠`record_id`と対応付ける。同一案件の重複を避け、類似名だけで異なる案件を統合しない。
3. **先週の進捗・課題**：見積依頼・提出、顧客要望、商談進展、停滞、要対応事項を商談記録から抽出。配下分は`deal_records`のみ参照し、他人の`todo_tasks`を利用しない。社長職は重要事項最大5件。
4. **今週の予定・計画**：本人商談記録にある今週の明確な予定、本人の期限付きToDo。日付不明の対応は別区分。Googleカレンダーを参照しない。記録にない予定・期限を生成しない。
5. **本人の未完了ToDo**：本人所有の`todo_tasks`のみ。今週期限・期限超過・期限なしに分け、内容・期限・重要度を原則そのまま表示。

社長職は会社全体の集計・営業所別内訳を示し、個別案件は上限内に圧縮する。今週の予定とToDoは社長本人のみ。情報量の制御のために会社全体の件数集計を省略しない。

## 5. AI処理と確認可能性
- AIは「主な商談」「進捗・課題」の要約・選定に使う。件数等の数値はGASで集計し、AIの推定値にしない。
- AIへ渡した対象行IDの一覧、採用結果、選定理由、集計期間・役職・対象範囲、元データの対応を検証証跡に残す。個人情報や全文を`push_log`に独断で新規保存しない。
- 予定・商談の存在や受注確度・金額を補完しない。モデルの出力は元記録で検証し、根拠不一致ならNG。
- `weekly_manager`等の配信種別名称・ログキーは既存連携を確認し、独断変更しない。

## MAIL-00現行調査反映（2026-11-04）

### 現行実装との照合結果

- ローカル `src/06_output.gs` には `triggerWeeklyReport` と `generateWeeklyManagerReport_` があり、非手動実行時は月曜・7時でない場合にスキップします。これは本番トリガー登録の証拠ではありません。
- 本番 `output_config` には `weekly_enabled=TRUE`、`weekly_send_day=1`、`weekly_send_hour=8` が存在しますが、ローカルの週次処理はこの設定値をそのまま実行時刻判定に使用していません。設定値とコードの時刻判定に差があります。
- 本番 `todo_tasks` では、関東販売のpresidentのうち1名に本人TODOが存在します。ローカル `src/07_todo.gs` の `TODO_TASKS_ALLOWED_ROLES_` と `isTodoViewerRole_` はpresidentを許可していません。したがって、president本人TODOはデータとして存在しても、現行ローカルのTODO画面・取得処理の対象外です。
- GitHub `main` の `src/06_output.gs` は旧Chat通知系で、ローカルの週次メール実装とは一致しません。

### MAIL-02への反映方針

MAIL-02では、週次メールの対象役職・集計範囲・本人TODOの扱いを、現行コードで確認できる範囲と、承認が必要な仕様に分けて記載します。president本人TODOを週次メールへ含める場合は、TODO取得権限の変更と週次本文への組み込みを別途承認・実装する必要があります。本調査では権限変更を行いません。

本改修の適用範囲は関東販売に限定せず、正本で定義された全対象拠点・全対象地域です。関東販売の確認結果は代表的な現状証拠として記載しており、他拠点の配信対象・地域判定・送信実績を関東販売の結果から推測しません。
